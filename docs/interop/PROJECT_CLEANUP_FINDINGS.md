# Project cleanup findings and boundaries

This document records cleanup constraints discovered while preparing Gates 5 and 6. It deliberately separates verified facts from work that still needs profiling or call-site analysis.

## State ownership

- The product particle stride remains the compact, hot-path representation.
- `src/physics/relationshipState.js` provides compact relationship-state helpers and canonical pair indexing.
- `src/state/sparseRelationshipGraph.js` provides a bounded semantic graph with typed edges and pair history.
- These are not interchangeable data structures. The graph must not be wired into the solver until stable identity, persistence ownership, scheduling and migration are specified.

## Simulation correctness boundaries

- The product exact CPU solver remains the reference behavior.
- SIM shadow execution remains diagnostic and opt-in.
- Approximate backends require force-error and stability evidence, not timing alone.
- PRNG compatibility must preserve existing product draw order unless a consumer-by-consumer migration has explicit golden fixtures.

## Generated documentation ownership

- Canonical specs are generated by `scripts/generate-spec.mjs`.
- UI module documentation is generated by `scripts/generate-ui-module-report.mjs`.
- Generated files should be changed by their generators, then reviewed as ordinary source diffs.
- `docs:triple-pass` runs these generators before consistency checks and never commits or deploys.

## Deferred cleanup

No broad module rewrite, import-cycle rewrite, hot-loop abstraction, or data-layout change is included without a measured baseline and call-graph evidence. These are candidates for focused follow-up PRs, not permission to perform speculative refactors.
