03 / Population scale

10,000 is the hard cap—not a speed guarantee

The launch control and particle pool now share a 10k ceiling; runtime still depends on active laws, density, device, renderer, and frame-time quality adaptation.

Population envelope

Startup target → hard allocation limit; the intervening settings still constrain realized population.

Known solver work at scale

Code reading, not measurements: these explain why the slider change alone cannot cure lag.

  • Every tick rebuilds a spatial grid from alive particles.
  • Pair-neighbour work is bounded by interaction and neighbour caps.
  • QUALITY_MODE reduces the pair budget with population (approximately inverse square-root).
  • AUTO_TUNE selects grid dimension with ∛(N / 1.4), clamped to 12–64.
  • Heavy law families add their own per-particle / pair work.
  • At 10k and defaults, the adaptive pairwise budget is roughly 48/particle at 60-FPS target (from 96/√4), before other solver phases.
Documentation drift to correct: the solver’s surrounding explanation says the density target is about 0.5 particles/cell, but the active grid expression divides population by 1.4 before taking the cube root. Reconcile the comment with the formula and measure grid-build versus pair-search cost before tuning either constant.
04 / Fidelity map

Approximate the right subsystem, explicitly

Performance modes should announce which physical detail they trade away. Fast paths are not universal accelerators when their data assumptions do not match a law.

Gravity choices

Exact (default)
Pairwise GRAV preserves pair-specific modifiers, but contributes to neighbor-loop cost.
Barnes–Hut (opt-in)
Octree far-field drops DNA FORCE / TIDAL / HIDDEN_MASS modifiers and star-collapse boost. This is an explicit fidelity trade.
FMM (opt-in route)
Alternative gravity implementation exists; validate error, stability and interaction with other forces before recommending as default.

GPU path is not the whole solver

The synchronous solver accepts externally computed gravity/collision force buffers; its comments explicitly say it retains full law semantics instead of silently switching dispatch based on the compute preference. The browser worker has WebGPU force code, but that does not imply every law or cost moves to GPU.

05 / Reorganization

Make the controls tell users what changes

149 controls are a broad modeling surface. The most urgent improvement is not adding many new sliders—it is separating operational controls from model semantics.

Proposed top-level groups

  1. Population & scale — INITIAL_POP, MAX_POP, pool cap, WORLD_SIZE, density.
  2. Performance — renderer, compute route, grid, interaction budget, cadence, quality target.
  3. Environment — fields, boundaries, gravity wells, temperature, radiation.
  4. Physics & mechanics — forces, contacts, bonds, topology, conservation.
  5. Life & society — biology, information, groups, governance, infrastructure.
  6. Matter & time — chemistry, thermodynamics, exotic matter, relativity, quantum, epochs.

Principles

  • Keep per-species DNA distinct from world-wide parameters.
  • Organize laws by mechanism plus dependency graph; surface prerequisites and “no-op without X” state.
  • Show actual effective value, source (preset / override / default), and range.
  • Badge verified legacy/no-op controls; do not silently present a stale control as active.
  • Expose density and estimated neighborhood pressure beside population/world size.

Current source: src/state/worldParams.js · src/constants/laws.js · src/ui/paramHelp.js

06 / Gaps to fill

Priorities for real-time scale and scientific trust

Proposals below follow confirmed wiring and documentation mismatches; no performance wins are claimed without representative timing and parity tests.

P0
trust

Make parameter metadata executable and auditable

Build a coverage check that compares WORLD_PARAM_DEFS keys against actual runtime reads, defaults, UI help, preset values and reset/serialization paths. Mark confirmed legacy controls explicitly; candidate stale controls include CENTRIPETAL_SCALE, ROTATION_SPEED, TURBULENCE_KICK and TIME_WARP_FACTOR (their help labels them legacy/no-op). Do not remove until callsites are audited.

P0
perf

Profile one canonical 10k launch end-to-end

Record warm and steady-state physics tick p50/p95, render frame time, worker wait, neighbor count, grid rebuild time, allocations, active laws, device and backend. Compare 1k / 2.5k / 5k / 10k with identical seeded world and toggles; preserve both correctness metrics and FPS. Existing Node solver benches do not substitute for browser GPU/renderer measurements.

P1
perf

Budget by measured cost, not particle count alone

Expose a quality target that considers density, candidate count and law-family cost. Add per-phase timing and a stable “fidelity preset” that says which interactions are skipped/cadenced. Validate deterministic repeatability and quantify the effect of adaptive truncation on contact, predation, bonding and chemistry.

P1
fidelity

Decide whether to add a physical ground/boundary model

There is no GROUND_HEIGHT parameter or ground plane in the current spawn/physics contract. All initial and later background spawns sample Z uniformly from the full world height, independently of XY shape and centre bias. If a floor is desired later, it needs explicit contact, restitution, friction and energy accounting, plus tests with WRAP/toroidal and soft-wall modes.

P1
fidelity

Use parity envelopes for approximate engines

For exact/BH/FMM/GPU compare, fix seed and initial state, sweep population and force modifiers, report RMS/max force error plus trajectory divergence and conserved quantities. Barnes–Hut’s known modifier omission should be a visible mode trade, not a hidden default change.

P2
model

Fill model gaps only after dependency mapping

Candidate capabilities: explicit collision ground/terrain; conserved energy/momentum diagnostics; per-law applicability and dependency conditions; force-law parameter sensitivity maps; richer density-aware launch presets. Prefer closing schema/help/runtime coverage over adding speculative law toggles.

07 / Answer in brief

Spawn height is uniform

Every initial particle and later background spawn chooses z uniformly from the full range [0, WORLD_SIZE). The XY SHAPE and centre-bias controls do not constrain spawn height. There is no GROUND_HEIGHT setting or persistent ground plane in the current simulation.

Verified in src/main.js and src/spawn/distribution.js; deterministic regression coverage in tests/audit/params_batch_01.test.js.
