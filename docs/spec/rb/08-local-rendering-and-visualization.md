# 08 — Local renderer and visualization

**Current evidence:** `src/render/renderer.js` provides Canvas2D; `createRendererAsync` optionally loads `pixiRenderer.js` and falls back to Canvas2D. `src/render/spriteSync.js` dispatches by backend. Rendering reads a particle buffer, uses `dna/expression.js` for color/radius/alpha, camera projection from `src/ui/camera.js`, phenotype caching and off-screen culling. There are two canvas layers for background and simulation. This describes the current implementation, not the selected product direction. The accepted roadmap selects GPU-rendered 3D; the transition is not implemented or browser-verified.

## Target boundary

The target presentation direction is GPU-rendered 3D, as selected by the accepted roadmap. Renderer consumes a backend-neutral, immutable `RenderFrame`/typed view: positions, presentation attributes or stable particle IDs, world/camera metadata, effects, tick/time and completeness/version. It does not own simulation state, decide authoritative law outcomes, or depend on worker/cloud implementation. Local rendering persists during cloud processing: snapshot arrival, interpolation, camera transform, canvas layout, overlays, and UI are browser responsibilities. Preserve current visual identity and state-faithful overlays; do not equate the current Canvas2D/Pixi implementation with the target renderer. If GPU 3D is unavailable, explain the capability loss and offer explicit disable/fallback choices rather than silently changing simulation state.

Renderer adapter lifecycle: capability probe → initialize → resize/DPR → render coherent frame → report metrics/backend → dispose. GPU-rendered 3D is the selected target; the specific graphics API and explicit fallback choices remain implementation decisions. Existing Canvas2D/Pixi paths are current compatibility/fallback options, not the target reference. Rendering GPU capability is distinct from GPU simulation/compute capability. Avoid duplicating CPU math or semantics in shaders without differential/visual tests. Cache by world/frame identity, not a global mutable view that can mix sessions. Respect DPR caps, visibility/off-screen culling, device loss and reduced-power modes.

## Acceptance

Capture representative screenshots across viewport sizes, drawer expanded/minimized/hidden, different law palettes, particle densities, selection/hover/help and settings mode. Match layout, active states, color/contrast, touch targets and 3D camera projection within reviewed tolerance. Verify frame consistency: no torn mixture of tick versions; interpolate only across compatible snapshots and do not overshoot boundaries. Report render FPS/frame time separately from simulation TPS/tick latency and network freshness. Benchmark the selected GPU-rendered 3D path on the fixed reference hardware; separately measure any explicit fallback path and describe capability loss. Browser validation must run on real browser engine; DOM stubs do not prove rendering.
